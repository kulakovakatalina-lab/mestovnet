# Ежемесячная актуализация заведений и артистов

Процедура для регулярного (раз в месяц) обновления `venues.json`/
`artists.json`: новые заведения/артисты получают карточки, устаревшие
описания переписываются, находки по дублям/корректности идут на ручное
решение. Запускается плановой задачей (cron) — она открывает PR и **не
мержит и не пушит в main сама**, финальное решение всегда за человеком
(«Выложи …», как обычно).

## Порог «описание пора переписать»

`build_venues.py`/`build_artists.py` хранят `desc_baseline_count` — снимок
`event_count` на момент последней ручной правки описания. Описание считается
устаревшим и попадает в отчёт билдера («Требует обновления описания»), если:

- описания нет вовсе (новое заведение/артист), либо
- `event_count` вырос относительно `desc_baseline_count` минимум на **5
  событий абсолютно** или **на 30% относительно** (что сработает раньше).

## Шаги

1. В главной папке `MestovNet`: `git pull origin main --ff-only`, затем
   `git worktree add ../MestovNet-actualize-YYYY-MM -b feature/actualize-YYYY-MM main`.
2. В новом worktree: `python build_venues.py` и `python build_artists.py`.
   Оба перезаписывают venues.json/artists.json и печатают отчёт; рукописные
   `description`/`lat`/`lon` переживают пересборку (мердж по slug, с
   фолбэком на имя — см. комментарии в коде).
3. Из отчёта собрать три списка:
   - **новые** заведения/артисты — слага не было в старом файле (`git diff`
     по `venues.json`/`artists.json` покажет добавленные записи);
   - **«Требует обновления описания»** — печатается самим билдером;
   - **«Возможные дубли»** — печатается самим билдером. Точные/транслит-
     совпадения и всё, что уже в курируемых `MERGE_GROUPS`, слились
     автоматически ещё на этапе билда — в этом списке только спорные
     случаи, их **не сливать самостоятельно**, а вынести на решение
     пользователя в PR (шаг 8).
4. Для каждой записи из списков «новые» и «требует обновления описания»:
   прочитать её события в `events.json` (по `venue`/`aliases` или
   `artist`-совпадениям), прочитать старое описание, если было (для
   стиля), и написать новое — кратко, по делу, в духе существующих карточек.
   Избегать формулировок с жёстким окном времени («за последний месяц») —
   они устаревают быстрее, чем наступит следующий прогон; предпочитать
   факты, которые не протухают (жанры, состав, статус, заметные
   выступления). После записи описания — обновить `desc_baseline_count`
   этой записи на текущий `event_count`.
5. `python geocode_venues.py` — дозаполнит координаты новых заведений
   (идемпотентен, трогает только пустые lat/lon).
6. `python generate_pages.py` — пересобрать все страницы, включая новые
   `venues/<slug>` и `artist/<slug>`.
7. Прогнать пре-релизные автотесты локально:
   `pytest tests/test_data_integrity.py tests/test_generated_pages.py tests/test_sitemap_robots.py tests/test_layout_playwright.py`
   Если что-то красное (и это не известный ratchet-долг из
   `tests/conftest.py`) — остановиться и разобраться, не коммитить.
8. Закоммитить, запушить ветку, открыть PR (`gh pr create`). В тело PR — что
   нового (заведения/артисты), что переписано, и **полный список подозрений
   на дубли** из шага 3 для решения пользователем. Дальше — как обычная
   фича: пользователь смотрит PR и говорит «Выложи …», когда готов.

## Не автоматизировано намеренно

- Слияние спорных дублей — только по решению пользователя.
- Смена канонического написания/города/адреса заведения — тоже ручное
  решение (курируемые `MERGE_GROUPS`/`EXCLUDE_KEYS`/`EXCLUDE_ARTISTS` в
  билдерах, как и раньше).
- Запуск самого парсера (`parser.py`) в эту процедуру не входит — он
  запускается отдельно и только с явного разрешения пользователя.
